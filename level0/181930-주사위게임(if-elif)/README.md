## 왜 어려웠나 (헷갈렸던 부분)

- **비교 연산자를 연달아 쓰면 "앞뒤로 인접한 것끼리만" 비교된다는 걸 몰랐음**
  → `a != b != c`는 파이썬에서 `(a != b) and (b != c)`로 해석됨. `a`와 `c`가 같은지는 전혀 확인 안 함
  → 반례: `a=3, b=5, c=3` (a와 c가 같고 b만 다른 경우) → `a!=b`(True) and `b!=c`(True) → 전체가 True로 잘못 판정되어, "두 개만 같은 경우"인데 "셋 다 다른 경우"로 착각함
  → 세 개 이상이 "전부 서로 다른지" 확인하려면 모든 쌍을 각각 명시해야 안전함: `a != b and b != c and a != c`

- **`elif`가 항상 안전하다고 착각함 — 실제론 "조건 자체가 정확할 때만" 안전함**
  → elif로 연결했더니 오히려 틀렸고, 그냥 if 세 개를 따로 썼더니 정답이 나옴
  → 이유: 1번째 조건(`a != b != c`) 자체에 버그가 있는 상태였음
    - elif로 연결하면: 버그 있는 1번째 조건이 잘못 걸리는 순간, 그 틀린 결과가 그대로 굳어짐 (아래 조건이 검사도 안 되니까)
    - 그냥 if를 세 번 따로 쓰면: 1번째가 잘못 걸려도 2번째 if가 독립적으로 다시 검사하고, 마침 그 케이스에서 2번째 조건도 True가 나와서 답이 덮어써져 우연히 정답이 나옴
  → 즉, "if만 쓴 코드가 맞았던 이유"는 좋은 스타일이라서가 아니라, 1번 조건의 버그를 2번 조건이 우연히 땜빵해주는 구조였기 때문. elif를 빼는 게 본질적 해결책이 아니라, 1번 조건 자체를 정확히 고쳐야 하는 문제였음

## if만 사용할 때 vs elif를 사용할 때 차이점 정리

| 구분 | if만 나란히 쓸 때 | elif로 연결할 때 |
|---|---|---|
| 실행 방식 | 모든 if를 항상 하나씩 다 검사함 (앞에서 조건이 걸려도 뒤엣것도 검사) | 앞의 조건이 True면, 뒤는 검사 자체를 안 하고 건너뜀 |
| 값 처리 방식 | 뒤에서 조건에 걸리면 answer를 계속 덮어씀 → 최종적으로 "마지막에 걸린 조건"의 결과가 남음 | 처음 걸린 조건의 결과가 그대로 최종 답이 됨 |
| 앞 조건에 버그가 있을 때 | 뒤 조건이 우연히 다시 검사해서 값을 정정해줄 "기회"가 있음 (단, 우연에 의존하는 것이라 좋은 설계는 아님) | 앞 조건의 버그가 그대로 최종 결과로 굳어짐, 정정 기회 없음 |
| 안전하게 쓰는 법 | 각 조건이 서로 겹치지 않게 설계했다면 상관없이 안전함 | "각 조건이 정확하게 그 경우만을 판별한다"는 게 보장될 때만 안전함 |

## 배운 점

- 세 개 이상의 값이 "모두 서로 다른지" 확인할 땐, 모든 쌍을 각각 `and`로 명시해야 한다. `a != b != c`처럼 연쇄해서 쓰면 인접한 쌍끼리만 비교되어 놓치는 경우가 생긴다.
- `elif`는 만능 안전장치가 아니다. **위에 있는 조건 자체가 정확할 때만** elif가 안전하게 동작한다. 조건에 버그가 있으면 elif는 그 버그를 그대로 최종 결과로 확정시켜버릴 뿐이다.
- 여러 개의 배타적인 경우(다 같음 / 일부만 같음 / 다 다름)를 나눌 땐, "가장 좁은/특수한 조건부터" 위에 놓고, 마지막은 `else`로 "나머지 전부"를 받게 설계하면 조건 자체의 정확도에 덜 의존하게 되어 더 안전하다.

## 최종 풀이
```python
def solution(a, b, c):
    if a == b == c:
        return (a+b+c) * (a**2+b**2+c**2) * (a**3+b**3+c**3)
    elif a == b or b == c or a == c:
        return (a+b+c) * (a**2+b**2+c**2)
    else:
        return a + b + c
```
